# 产品产物与文档结构

> 说明 PM Skills 产生的文档、每个文档的目的、使用阶段和上下游关系。本文面向维护者和使用者，不参与 Agent 运行时加载。

## 1. 标准目录

产品经理工作流默认使用：

```text
docs/product/<feature-slug>/
├── 00-route.md
├── 01-brief.md
├── 02-strategy.md
├── 03-experience.md
├── 04-prd.md
├── 05-metrics.md
└── 06-review.md
```

不是每个需求都需要全部文件。小改动可以使用 Lean PM 路径，把必要内容合并到 brief 和短 PRD。可选文件必须标记 `not-applicable` 并写明原因。

## 2. 每个文档的目的

| 文档 | 目的 | 主要负责 | 上游 | 下游 | 适用规模 |
|---|---|---|---|---|---|
| `00-route.md` | 记录产品工作规模、产物计划、PM 视角发现和门禁状态 | PM / 需求负责人 | 原始请求 | 所有后续产物 | S/M/L |
| `01-brief.md` | 定义问题、用户、价值、MVP、指标、备选方案和 go/no-go | PM | 原始请求、业务背景 | strategy、experience、PRD | S/M/L |
| `02-strategy.md` | 说明产品选择、价值主张、优先级、取舍、MVP 和路线图 | PM | brief | experience、PRD | M/L |
| `03-experience.md` | 定义用户旅程、信息架构、状态、权限、异常和业务规则 | PM / UX | brief、strategy | PRD | M/L |
| `04-prd.md` | 把产品方案展开为可执行、可测试的需求和验收标准 | PM | brief、strategy、experience | 研发、测试、计划 | S/M/L |
| `05-metrics.md` | 定义成功指标、护栏、埋点、基线、目标和复盘计划 | PM / 数据 | brief、PRD | 上线测量、复盘 | M/L |
| `06-review.md` | 汇总产品评审、追踪矩阵、风险、未决问题和交接结论 | PM | 所有上游产物 | 研发、测试 | M/L |

## 3. 各文档的详细职责

### `00-route.md`

记录这次产品工作要走哪条路径：

- `S/M/L` 规模判断和理由；
- 必需和可选的产物；
- 每个产物使用的 Skill；
- 当前门禁状态；
- 六类 PM 视角发现；
- 下一步动作和负责人。

它解决的是：非产品经理不知道应该先做什么、做到什么程度、什么时候可以交给下游。

### `01-brief.md`

一页产品判断文档，回答是否值得做、为谁做、做到什么程度。

必须包含：

- 问题和当前代价；
- 目标用户和场景；
- 期望结果；
- 成功指标和护栏；
- MVP、范围和明确不做的事；
- 备选方案和推荐结论；
- 假设、风险和未决问题；
- go / pilot / defer / reject / needs-discovery。

### `02-strategy.md`

回答为什么选这个方向，以及为什么现在做。

应包含：

- 产品目标和价值主张；
- 用户、市场和业务背景；
- 方案比较；
- 优先级和取舍；
- 路线图和阶段性目标；
- 关键依赖、风险和停止条件。

### `03-experience.md`

回答用户如何完成任务，以及系统如何处理异常和权限。

应包含：

- 端到端用户旅程；
- 入口、信息架构和角色；
- 状态、状态流转和操作按钮；
- 权限、数据范围和可见性；
- 空状态、加载、错误、部分成功和恢复；
- 业务规则、例外和审批；
- 可供 PRD 展开的交互验收点。

### `04-prd.md`

回答研发和测试如何理解并执行需求。

应包含：

- 执行摘要；
- 用户故事和场景；
- 功能需求和业务规则；
- 验收标准；
- 非功能要求和约束；
- 数据、权限、状态和异常；
- 风险、依赖和未决问题；
- 范围和非目标。

PRD 不负责技术架构、测试用例设计或发布实施细节。

### `05-metrics.md`

回答上线后如何知道是否成功。

应包含：

- 主要结果指标；
- 领先指标；
- 护栏指标；
- 基线、目标、时间窗口和数据来源；
- 事件和属性定义；
- 埋点验证方式；
- 复盘日期和决策人。

### `06-review.md`

回答产品工作是否可以交接。

应包含：

- 六类 PM 视角的评审发现；
- 需求到体验、规则和指标的追踪矩阵；
- 阻塞项、风险、假设和未决问题；
- 交接包清单；
- 最终 gate 结论；
- 仍需研发或测试澄清的内容。

## 4. 其他 Skill 产物

除 PM 工作流外，仓库中的一些 Skill 会按约定生成其他文档：

| Skill | 产物路径 | 目的 |
|---|---|---|
| `brainstorming` | `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` | 记录探索后的设计方向、方案取舍和需要批准的设计 |
| `writing-plans` | `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md` | 记录文件级实施任务、测试步骤、验证命令和交接顺序 |
| `requesting-code-review` | 由调用方指定的审查记录 | 保存变更摘要、需求映射、验证证据和审查发现 |
| `verification-before-completion` | 由调用方指定的验证记录 | 保存命令、输出、通过/失败项和未验证风险 |

PM 产物是研发和测试的输入；实施计划、技术设计和测试设计应作为下游专业产物，不反向混入 PRD。

## 5. 追踪编号

| 前缀 | 用途 |
|---|---|
| `FEAT-*` | 功能或产品计划 |
| `REQ-*` | 可测试需求 |
| `UX-*` | 用户旅程、状态或交互规则 |
| `RULE-*` | 业务规则或例外 |
| `METRIC-*` | 指标、护栏或埋点 |
| `DEC-*` | 产品决策 |
| `RISK-*` | 风险 |
| `OPEN-*` | 未决问题 |
| `ASSUME-*` | 待验证假设 |

推荐链路：

```text
FEAT → REQ → UX / RULE → METRIC → DEC
```

每个需求至少应能追踪到用户结果、体验或规则，以及一个验收标准。

## 6. 文档状态

| 状态 | 含义 |
|---|---|
| `draft` | 正在编写 |
| `review` | 等待产品或跨角色评审 |
| `approved` | 门禁通过，可作为下游输入 |
| `blocked` | 缺少关键决策、输入或产物 |

没有评审记录、没有验收标准或存在关键未决问题时，不应标记为 `approved`。

## 7. Lean PM 路径

小改动可以压缩为：

```text
docs/product/<feature-slug>/
├── 00-route.md
├── 01-brief.md
├── 04-prd.md
└── 06-review.md
```

前提是：

- 不引入新的业务模型或权限模型；
- 不改变关键用户旅程；
- 不需要独立的产品策略；
- 现有指标足以判断结果；
- 风险低且可逆。
